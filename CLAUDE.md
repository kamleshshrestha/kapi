## Project

Kapi (formerly Learning Debugger) — a web app that helps beginner machine-learning learners identify *specifically* what they misunderstand about a concept, rather than giving them another generic explanation.

The learner experience is a chat-first session with flashcards, available for all six catalog concepts (gradient descent, backpropagation, overfitting, train/test split, linear regression and logistic regression). It is served from the root (the earlier quiz-style v1 flow has been removed; the old `/v2/...` URLs redirect to the root ones via `next.config.ts`, and the `v2` names in the API path, component/lib folders and localStorage keys are kept so stored learner data doesn't change). A concept in `lib/learning/concepts.ts` without misconceptions has no Core flashcards and the chat cannot diagnose it. Each misconception in `lib/learning/misconceptions.ts` carries a hand-written `example` shown to the learner as written (the field is optional, and a misconception without one falls back to an example the model invents, which is where the measured content errors were); `tests/lib/learning/diagnostic.test.ts` holds them to being short, plain, numeric and present on every entry. Unit tests run with Vitest.

The home page opens with the promise, a three-step intro and a collapsed "See what a session looks like" example (`lib/learning/v2/sampleExchange.ts`, rendered with the real `ChatBubble`; collapsed so the concept list stays above the fold); a footer on every page links Send feedback (`/feedback`), Privacy and Impressum (`/impressum`: name, postal address and email of the private individual who runs Kapi).

Teach-it-back (`/teach/[concept]`, linked from the end of a chat): the learner explains the concept to Kapi playing a curious beginner for `TEACH_TURNS` (3) messages via the `teach` phase of `/api/v2/chat`; the beginner only asks naive questions (prompt `chatTeachPrompt`) and the assessment (solid/partial/shaky, what was clear, gaps) is returned only on the last turn, enforced by the route. A solid one counts as clean Defend evidence. Chat events of this mode are not written to the opt-in log yet.

Learner flow: pick a concept (`/`) → explain it in your own words in a chat with Kapi → the LLM finds the specific gap (or compliments a strong explanation and challenges it) → a checkpoint: the reaction and the fix arrive on their own, and Kapi asks whether that landed before the example and first question follow ("Makes sense" / "I have a question", `lib/learning/v2/gate.ts` + `GateChips`, phase `await-gate`; static copy, no LLM call; skipped for a strong explanation, which was taught nothing) → an adaptive conversation of up to 7 questions that builds the learner up (small teaching pieces, easy guiding questions) before checking and only then challenging, with hints before reveals and help chips (hint / "I'm lost" / explain differently) → a recap at the end. Every piece Kapi says is its own chat message (feedback, teaching, question), not paragraphs of one, which `TUTOR_VOICE` tells the model. The diagnosis may also return one `formula`: how much maths a learner wants is read from how they write (notation or mathematical vocabulary in their own explanation means give the standard form; everyday words means only where it is clearer, and then the explanation names every symbol first), rather than from a beginner/advanced toggle, which learners self-assess badly and which would double the prompt and eval surface. It is plain text, not LaTeX: the app has no renderer, so `cleanFormula` (`lib/learning/v2/formula.ts`) drops anything with markup, without a relation symbol or over 120 chars rather than show a beginner the source, and `ChatBubble` renders `kind: "formula"` as a wrapping monospace block. At any point the learner can type a question of their own instead of answering rather than being graded on it: the `check` call classifies the message (`learnerIntent`, where a hedged or wrong attempt still counts as an answer), and a question is answered by a separate `chatQuestionPrompt` call (route helper `answerLearnerQuestion`, shared with the explicit `question` phase that the checkpoint uses, where `probeQuestion` is null because Kapi has asked nothing yet and so the reviewer is skipped) whose reply goes through `guardQuestionReply` (`lib/llm/leakGuard.ts`), because the question may itself be the answer to the one still pending. That reviewer is deliberately not `guardAgainstLeak`: the hint reviewer rewrites a leak into a one-sentence nudge, which would throw away the answer the learner asked for, so this one trims only the giveaway (a yes/no on the pending example, calling it good or bad, naming what it is an instance of) and keeps the explanation; if it fails or returns a near-empty rewrite, the tutor's reply is shown as written. Such a turn costs no turn, verdict, flashcard or depth-level evidence, and is counted as `learner_question` but not written to the opt-in log (`session_events.result` has no value for it). Resolved ideas and shaky ideas are saved as personal flashcards ("From you" deck, alongside the catalog-derived "Core" deck at `/decks/[concept]`). A too-thin first explanation falls back to the first diagnostic question's options as quick replies.

## Commands

Package manager is pnpm (`packageManager: pnpm@10.33.0` in package.json).

- `pnpm dev` — start the dev server (http://localhost:3000)
- `pnpm build` — production build
- `pnpm start` — run the production build
- `pnpm lint` — run ESLint (flat config in `eslint.config.mjs`, extends `eslint-config-next`'s core-web-vitals and typescript rule sets)
- `pnpm test` — run the Vitest unit tests once (`pnpm test:watch` to watch). Config is `vitest.config.mts`; tests live in `tests/**/*.test.{ts,tsx}` and use the `@/` alias. Covered so far: `lib/learning/` (incl. the content rules and `v2/` helpers), `lib/llm/` (`client.ts`, `rate-limit.ts`, `schemas.ts`, `scrub.ts`; in `client.ts` tests fetch is stubbed with `vi.stubGlobal` and backoff uses fake timers), the `/api/v2/chat` route (`tests/app/api/v2/chat/route.test.ts`), the `useV2ChatSession` and `useFlashcardDeck` hooks (`tests/hooks/`) and the v2 chat/flashcard components (`tests/components/v2/`). Hook and component tests run in jsdom via a `// @vitest-environment jsdom` docblock with `@testing-library/react`, and also import `@testing-library/jest-dom/vitest`.

- `pnpm stats [days]` — print usage numbers from Supabase (default 14 days; `scripts/stats.mjs`, runs `psql` against `POSTGRES_URL_NON_POOLING` from `.env.local`): per-day and per-concept counts from `analytics_daily` (chats started and finished, teach-it-back, model errors, refused requests) and how many accounts that turned on "Save my progress" came back on a later day. Read-only.
- `pnpm eval` — run the evaluation set (`evals/`, 24 hand-labelled learner explanations for diagnosis, config `vitest.eval.config.mts`) against the real model: diagnosis accuracy by exact misconception id, plus whether first-miss hints leak the answer, judged by a different model (`EVAL_JUDGE_MODEL`, default `openai/gpt-oss-120b`) before and after the production reviewer pass (`lib/llm/leakGuard.ts`). It needs `OPENROUTER_API_KEY` in `.env.local`, costs a few cents (about 2.5 minutes), is not part of `pnpm test`, and writes texts and results to `evals/last-run.json` (gitignored). Thresholds are a tripwire (LLM judge, small sample); the label sanity checks run in `pnpm test` (`tests/evals/`). A 2026-10-12 run on Haiku 5.5 gave 24/24 diagnoses, 2/18 raw and 0/18 guarded leaks. It also judges whether the diagnosis told the learner anything untrue (`accuracyCheckPrompt`, judge model, against the hand-written catalog correction): two 2026-10-15 runs gave 24/24 diagnoses and flagged 3/18 then 2/18 as inaccurate, and checking every flag by hand showed about half were real (a decision boundary called "the straight line between" two points not on it; an overall mean asserted from two halves without the split that would give it) and about half invented (correct backprop arithmetic called wrong, in both runs). Making it quote the text and show its arithmetic cut false positives without removing them. So treat the number as a floor, read the texts in `last-run.json`, and note there is deliberately **no** accuracy guard in production: at ~50% precision it would rewrite about as many correct explanations as wrong ones. `evals/teach.eval.ts` (12 scripted three-message explanations in `evals/teachCases.ts`, run by the same command) checks the teach-it-back assessor: verdict against the hand label, never crediting a wrong explanation as solid (a solid verdict is Defend evidence), gaps empty exactly for solid, and the beginner staying in role (judge model); a 2026-10-12 run gave 12/12 verdicts, 0 false solids, 1/36 role breaks. It writes `evals/last-teach-run.json` (gitignored).

## Architecture

- Next.js App Router (`app/` directory), TypeScript, Tailwind CSS v4 (via `@tailwindcss/postcss`, no `tailwind.config` file — v4 uses CSS-based config in `app/globals.css`).
- Path alias `@/*` maps to the repo root (`tsconfig.json`).
### Folder structure

```
app/
├── page.tsx                 concept selection (promise, intro, sync notice, email account)
├── learn/[concept]/         the chat session
├── teach/[concept]/         teach-it-back (explain to a beginner)
├── decks/[concept]/         flashcard review (Core + "From you" decks)
├── feedback/, privacy/, impressum/
└── api/v2/
    ├── chat/route.ts        chat phases: diagnose, check, assist, question, summary, teach (leak-checked hints);
    │                        a check turn the model marks as a learner question is answered by a
    │                        second, leak-checked call instead of being graded
    ├── feedback/route.ts    learner feedback (scrubbed, server-written)
    └── account/             DELETE (erasure) and export/ (JSON download)
components/v2/               ConceptSelectorV2, ChatThread, ChatBubble, ChatInputBar, QuickReplyChips,
                             AssistChips, GateChips, SessionSummary, FlashcardDeck, Flashcard
hooks/
├── useV2ChatSession.ts      chat state machine, checkpoint/help/hint/retry/recap, calls /api/v2/chat
└── useFlashcardDeck.ts      deck walk-through, self-rating, "review missed"
lib/
├── analytics/               counter.ts (countEvent, anonymous daily counters)
├── llm/                     client.ts (OpenRouter client, generateStructured, request helpers),
│                            prompts.ts, schemas.ts (zod request + structured-output schemas),
│                            scrub.ts (strips internal misconception ids from learner-facing model text)
└── learning/                domain logic, no React/LLM dependencies:
                             concepts.ts, misconceptions.ts, diagnostic.ts (question bank: content rules
                             below + quick-reply fallback), types.ts, v2/ (chatFlow limits, openers, gate,
                             flashcards, personalCards, flashcardMastery, localSession)
tests/                       mirrors lib/, app/, hooks/ and components/ (Vitest; `lib/llm/prompts.ts` is only partly covered through the route tests)
```

Conventions:
- LLM calls happen only in `app/api/*` route handlers via `lib/llm/`; components and hooks call the API routes and never import `lib/llm/` (keeps the API key server-side). Types shared with the client live in `lib/learning/types.ts`.
- LLM calls go to OpenRouter's chat-completions API via `fetch` (no SDK). The model is `OPENROUTER_MODEL` from the environment, defaulting to the free `qwen/qwen3.8-27b:free` (constant `MODEL` in `lib/llm/client.ts`). Free models are often rate limited or overloaded and take ~10-15s per call. A 10-case bake-off on 2026-10-11 (real prompts, all diagnoses correct on both) picked `anthropic/claude-haiku-5.5` as the recommended paid model (~4s per call, ~$0.0014 per diagnose+check case; set it via `OPENROUTER_MODEL`); `openai/gpt-oss-120b` was cheaper but leaked answers in its feedback and once skipped a first-miss hint. Requests send `provider: { require_parameters: true, data_collection: "deny" }` and deliberately no `temperature` (that combination returns a 404 on Haiku 5.5). Outputs are requested as JSON schema (from the zod schemas), then validated with zod and retried once on invalid output. The chat's conversation history comes back from the client on each turn, so it is treated as untrusted too. Model text shown to learners must not expose internal ids: the prompts forbid it and `/api/v2/chat` also runs every learner-facing field through `scrubMisconceptionIds`. First-try feedback and hints must not reveal the answer: the prompt says so, and a reviewer call (`guardAgainstLeak`) rewrites them if they do (falling back to neutral feedback if that call fails). `/privacy` tells learners that no name, email, account or IP address is sent to the AI service, that OpenRouter is a processor under its data processing agreement, and that data may be processed in the USA (the app uses the global `openrouter.ai` endpoint, not the Business-plan EU one); keep the request body free of identifiers, and change the page if the endpoint or model provider changes. Learner free text is untrusted: prompts wrap it in `<learner_...>` tags, and routes validate ids against the catalog server-side rather than trusting client-supplied misconception text.
- Secondary text never goes below `text-foreground/60` (lower opacities fail the 4.5:1 contrast in light and dark; enforced by `tests/a11y/textContrast.test.ts`), and standalone links and link-buttons get `py-2 -my-2` so their tap area is at least 32px tall without changing the layout.
- Diagnostic content rules (enforced by `tests/lib/learning/diagnostic.test.ts`): every question has exactly one correct option and its wrong options link to real misconceptions of the same concept; a concept has either both questions and misconceptions or neither; the correct answer's position varies within a concept; and the correct answer is not the longest option in more than half of a concept's questions, nor more than 60% longer than the longest wrong option (learners can otherwise guess "pick the longest").
- `lib/learning/` stays pure (no React, no LLM) so it is easy to unit test; shared types live in `lib/learning/types.ts`.
- Secrets go in `.env.local` (gitignored via `.env*`). It must contain `OPENROUTER_API_KEY` and may set `OPENROUTER_MODEL`; restart `pnpm dev` after changing it. Without a key the API routes return a 500 "AI service is not configured" error. The API routes have no auth, but each starts with `await checkRateLimit(request)` (`lib/llm/rate-limit.ts`): a fixed-window limit per client (default 20 requests per 10 min) plus a global cap (default 500 per hour), returning 429 with `Retry-After`. A signed-in learner is limited by their account id, anyone else by a salted HMAC of `x-forwarded-for`/`x-real-ip` (raw addresses are personal data and are never stored; set `RATE_LIMIT_SALT` to your own secret). Counters live in Upstash Redis when `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` are set (`lib/llm/rate-limit-redis.ts`: one pipelined REST call, INCR + PEXPIRE NX + PTTL, so the window is shared across serverless instances; keep the database in an EU region); if Redis is not configured or unreachable the in-memory limiter is used instead (logged once a minute), so learners are never blocked by an outage. Tune with `RATE_LIMIT_MAX`, `RATE_LIMIT_WINDOW_SECONDS`, `RATE_LIMIT_GLOBAL_MAX`, `RATE_LIMIT_GLOBAL_WINDOW_SECONDS`. The address headers are only trustworthy behind a proxy that sets them, and campuses share addresses, so consider a higher `RATE_LIMIT_MAX`. New LLM-backed routes must call it first.

### Deployment

- Deployed on Vercel (Next.js auto-detected, pnpm). `OPENROUTER_API_KEY` and optionally `OPENROUTER_MODEL` are set as Vercel environment variables, since `.env.local` is not deployed.
- The rate limiter uses Upstash Redis for shared counters: set `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` and `RATE_LIMIT_SALT` as Vercel environment variables. Without Redis it falls back to per-instance memory, which on Vercel rarely triggers and does not reliably protect the API key.
- Chat calls take ~10-15s with free models; if requests time out on Vercel, set `export const maxDuration` on `app/api/v2/chat/route.ts` (check the plan's limits).
- Learner data lives in browser localStorage first (`lib/learning/v2/` modules) and is optionally mirrored to Supabase (Frankfurt) once the learner opts in on the home page ("Save my progress"): `lib/sync/` merges the account into localStorage at startup and mirrors each local change (the modules emit events through `lib/learning/v2/changeEvents.ts`; `applyRemote*` writes are silent). Anonymous sign-in happens only after that opt-in (`lib/supabase/session.ts`). Schema lives in `supabase/migrations/` (apply with `psql "$POSTGRES_URL_NON_POOLING" -f <file>`; the CLI is old): `last_sessions`, `personal_cards`, `card_mastery`, `concept_levels`, `feedback` (written only by `POST /api/v2/feedback` with the secret key; text scrubbed and capped, `user_id` null without an account; asked after a finished chat and on `/feedback`), `consents` (append-only), `session_events` (opt-in log, written only by the server with the secret key after checking consent). `analytics_daily` holds anonymous usage counters (day, event, concept, detail, count; no identifier of any kind, so not personal data and kept without a retention job): the server adds one with `countEvent()` from `lib/analytics/counter.ts` (RPC `count_event`, executable only by the secret key, run after the response) for `chat_started`, `chat_finished`, `teach_started`, `teach_finished` (detail = verdict), `learner_question`, `model_error` (detail = status) and, batched at most once per 10 s per instance, `rate_limited`. Pass only values the server chose (catalog concept id, verdict, status), never learner text. Nothing is counted in the browser, so unique visitors, referrers and visits that never start a chat are not measured. RLS on every table, cascade delete from `auth.users`, pg_cron retention of 12 months. Learners can optionally attach an email to the anonymous account or sign in from another device with it (HIDDEN by default: the home page box and the "Email (optional)" section of `/privacy` only render when `NEXT_PUBLIC_EMAIL_SIGNIN=on` is set in `.env.local`/Vercel and the app is redeployed, see `lib/features.ts`; switch it on only after the Supabase email setup below, and fill in the "[provider]" sentence on `/privacy` first) (`lib/supabase/emailAuth.ts`, `EmailAccount` on the home page): always a 6-digit code typed into the app (`updateUser({email})` + `verifyOtp` type `email_change`; `signInWithOtp` with `shouldCreateUser: false` + type `email`), never a link, and the sign-in request never reveals whether an address has an account. It needs "manual linking" enabled in the Supabase dashboard and, beyond a couple of test mails per hour, a custom SMTP provider; the templates to paste are in `supabase/email-templates/`. Accounts with an email are kept 24 months of inactivity (anonymous ones 12). `/privacy` has the consent toggle, JSON export (`/api/v2/account/export`) and account deletion (`DELETE /api/v2/account`); the text has not had a legal review. Supabase needs `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY` (server only) in `.env.local` and Vercel. Depth levels (`lib/learning/v2/levels.ts`): Recognize/Explain/Apply/Defend, "solid" after three clean answers; the merge keeps the higher counts per level.
